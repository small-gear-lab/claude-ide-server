# 設計

状態: 草稿。ここに書いてあることは、まだ何も実装されていません。Claude Code の挙動についての記述は、既存の連携の観察と、公開されている解説に基づいています。Claude Code 本体で確かめていないものには **（仮定）** と付けてあります。

## 目標

- Claude Code のプロトコルを話す部分と、エディタを操作する部分を分けて、Claude Code の `/ide` をどのエディタにもつなげられるようにします。
- サーバーは、特定のエディタについて何も知らないままにします。エディタ側のアダプターは、サーバーと JSON-RPC で話す小さなプログラム（かプラグイン）です。
- 1 つのサーバープロセスで、複数のワークスペースを扱います。ワークスペースごとに、ロックファイルと WebSocket のポートを持ちます。
- 後始末をします。エディタがいなくなったら、そのロックファイルとポートも消えます。

## やらないこと

- Claude Code の CLI や、その端末を起動・管理すること。CLI は、利用者が動かした場所で動きます。`/ide` は、ロックファイルを通してサーバーを見つけます。
- WSL: Windows 上のエディタと、WSL の Linux 上の Claude Code（Issue #24）。サーバーと Neovim アダプタは、Windows そのものの上で動きます（「サーバーの実行」を参照）。
- 公式の連携の置き換え。公式の連携がないエディタのためのものです。
- すべてのワークスペースを代表する、ハブの入口。検討して、見送りました。CLI は、ふつう、エディタで開いているプロジェクトの中で動きます。同じディレクトリに合う入口が 2 つになると、`/ide` が迷うからです。

## 概要

```default
Claude Code ──WebSocket (MCP)──▶ claude-ide-server ◀──JSON-RPC (Unix socket)── editor adapter
   (1 per CLI)                    (1 process)                                    (1 per workspace)
```

サーバーには、2 つの顔があります。

- **Claude 側。** 登録されたワークスペースごとに、ループバックの WebSocket ポートで待ち受け、ロックファイルを書き、トークンで CLI を認証して、MCP（JSON-RPC 2.0）を話します。`initialize`、`tools/list`、`tools/call` に答え、通知を送ります。
- **アダプター側。** 1 つの Unix ソケットで待ち受けます。アダプターが接続して、ワークスペースを登録し、通知（選択範囲の変更、診断の変更）を送り、サーバーの要求（ファイルを開く、開いているエディタを返す、差分を出す）に答えます。

## Claude 側

既存の連携を観察して分かっていること:

- IDE は、10000〜65535 の乱数のポートで待ち受けます。バインドするのは `127.0.0.1` だけです。
- `~/.claude/ide/`（か `$CLAUDE_CONFIG_DIR/ide/`）に `<port>.lock` を書きます。中身は `pid`、`workspaceFolders`、`ideName`、`transport`（`"ws"`）、`authToken`、（JetBrains では）`runningInWindows` です。ファイルのモードは 0600、ディレクトリは 0700 です。
- CLI は、ヘッダー `x-claude-code-ide-authorization: <authToken>` を付けて、WebSocket でつなぎます。一致しなければ、閉じます（コード 1008）。
- メッセージは、MCP に基づく JSON-RPC 2.0 です。（ほかの実装のプロトコルのメモは、2025-03-26 としていますが、下で観察した CLI は、もっと新しい版を求めました。）
- CLI は、`initialize` を送り、続けて、自分の pid を付けた通知 `ide_connected` を送ります。

### 本物の CLI が送るもの

Claude Code 2.1.322 を、最小限だけ答える観察用のプログラム（`crates/core/examples/mcp_probe.rs`）につないで、分かったことです。

- **WebSocket のアップグレードは、サブプロトコル `mcp` を提示して、サーバーが 1 つも選ばないと、CLI は諦めます。** 最初の接続の試みが失敗したのは、まさにこの理由でした。CLI は、つないだ直後に、メッセージを 1 つも送らずに、接続を切りました。そのため、サーバーは、クライアントが最初に提示したサブプロトコルを返します。
- そのあと、この順に送ります。要求 `initialize`、通知 `notifications/initialized`、通知 `ide_connected`（`{ "pid": ... }`）、要求 `tools/list` です。
- `initialize` は、`protocolVersion` に `2025-11-25` を求め、`capabilities` には `roots`（`listChanged`）、`elicitation`、タスクの `extensions` を持ち、`clientInfo`（`name` は `claude-code`、`title`、`version`、`description`、`websiteUrl`）を付けます。同じ `protocolVersion`、`capabilities: { "tools": {} }`、`serverInfo` で答えるだけで足りて、CLI は `tools/list` に進みました。
- これで、`/ide` は、観察用のプログラムを `ideName` で一覧に出し、接続済みとして示しました。

### CLI が、ロックファイルを選ぶしくみ

Claude Code 2.1.322 で、インストールされた CLI を読んで分かったことです。

- **照合。** CLI は、自分の作業ディレクトリを、`workspaceFolders` の各フォルダと比べます（どちらも Unicode の NFC に正規化します）。フォルダが作業ディレクトリを含むとき（作業ディレクトリと同じか、その祖先）に、そのロックファイルを候補に出します。作業ディレクトリの中にあるフォルダは、条件が分かっていませんが、弱い一致として扱われます。それ以外は出しません。比べるのはパスの文字列で、シンボリックリンクを解決する処理は見当たりませんでした。だから、`workspaceFolders` には、利用者が `cd` で入るとおりのパスを書きます。
- **ポートの環境変数。** ポートが `CLAUDE_CODE_SSE_PORT` と同じロックファイルは、フォルダが何であっても、いつも候補に出ます。
- **順序。** ロックファイルは、新しいもの（更新時刻の順）から読みます。`/ide` は、合うものを並べます。同じ `ideName` が複数あるときは、見分けられるように、フォルダを添えます。自動接続は、最初の 1 つを取ります。
- **`pid`。** CLI は、`pid` がこのマシンで生きているプロセスではない（`kill(pid, 0)`）ロックファイル、読めないロックファイル、`pid` がなく、ポートが TCP 接続を受け付けないロックファイルを、消します。だから、`pid` は、アダプター自身の生きているプロセスでなければなりません。プロセスより長く残ったロックファイルは、次に見にきた CLI に消されます。
- **IDE の端末の中。** CLI が VS Code や JetBrains の端末の中（か、`FORCE_CODE_TERMINAL` を付けた状態）で動くときは、ロックファイルの `pid` が、自分の親プロセスか祖先（10 段まで）であることも求めます。ポートが `CLAUDE_CODE_SSE_PORT` と同じなら、この確認はありません。ふつうの端末では、この確認はありません。Neovim の `:terminal` は、Neovim がシェルの祖先なので、この条件を満たします。
- **通信の経路。** `transport` が `"ws"` なら、`ws://<host>:<port>` の WebSocket です。それ以外は、古い SSE の経路（`http://<host>:<port>/sse`）として扱います。ポートは、ロックファイルの名前から `.lock` を除いたものです。JSON ではないロックファイルは、1 行に 1 つのフォルダを並べたものとして読みます。
- **自動接続。** ふつうの端末では、CLI は、頼まれたとき（`/ide`）か、利用者が設定で自動接続を有効にしたときだけつなぎます。IDE の端末の中や、`CLAUDE_CODE_SSE_PORT` を付けたときは、自分でつなぎます。

試していないこと: `authToken` がないときの、CLI の挙動。

### Claude に公開するツール

ツールの集合は、VS Code の拡張が登録しているものです。サーバーが公開するのは、アダプターが登録のときに宣言したメソッド（下の `register` を参照）に裏付けられたツールだけです。JetBrains のプラグインが、VS Code の拡張より小さい集合を公開しているのと同じ考え方です。

| MCP のツール              | アダプターのメソッド            | 備考                                                                              |
|-----------------------|-----------------------|---------------------------------------------------------------------------------|
| `openFile`            | `openFile`            | `startText` / `endText` で、範囲を選ぶこともできます                                          |
| `openDiff`            | `openDiff`            | ユーザーが承認か却下をするまで待つ。`FILE_SAVED` と内容、または `DIFF_REJECTED` と タブ名を答える                |
| `close_tab`           | `closeDiff`           | `tab_name`（`openDiff` に渡したもの）で指定する。`TAB_CLOSED` を答える。そのタブがなくても、アダプタにメソッドがなくても同じ |
| `closeAllDiffTabs`    | `closeAllDiffs`       | `CLOSED_<n>_DIFF_TABS` を答える。アダプタに差分がなければ `CLOSED_0_DIFF_TABS`                   |
| `set_permission_mode` | `setPermissionMode`   | `{ mode }`。アダプタに対応するメソッドがなければ `OK` を答える                                         |
| `getOpenEditors`      | `getOpenEditors`      |                                                                                 |
| `getCurrentSelection` | `getCurrentSelection` |                                                                                 |
| `getLatestSelection`  | `getLatestSelection`  | 最後の選択範囲です。エディタのフォーカスが外れていても返します                                                 |
| `getWorkspaceFolders` | （サーバーが答えます）           | 登録の内容から返します                                                                     |
| `getDiagnostics`      | `getDiagnostics`      | 1 つの URI か、すべて                                                                  |
| `checkDocumentDirty`  | `checkDocumentDirty`  |                                                                                 |
| `saveDocument`        | `saveDocument`        |                                                                                 |

`executeCode`（Jupyter だけ）は、対象外です。

`closeAllDiffTabs` と `set_permission_mode` は、Claude Code 自身が、一覧に載っていたかどうかに関係なく呼ぶ（「Claude Code が自分から送るもの」を参照）。そのため、アダプタに対応するメソッドがなくても答える。一覧に載せるのは、アダプタが持っているときだけ。

ツール呼び出しの結末は、次のとおりです。

- ツール呼び出しの答えは、テキストの内容1つで、`openDiff` だけは2つです（`FILE_SAVED` と、そのあとにファイルの内容）。サーバーが VS Code の拡張機能のテキストに変換しないツール（残っているのは `set_permission_mode` だけ）では、アダプタが文字列を答えれば、それがそのままテキストになり、それ以外は JSON として書かれます。
- 失敗した呼び出し（アダプターがエラーで答える、時間内に答えない、いなくなった）も、答えのうちです。結果に `isError: true` と、理由のテキストが入ります。Claude は、理由を見られます。
- ツールの引数は、アダプターに聞く前に、そのツールのスキーマで検査します。必須の引数がない、または型が違うと、呼び出しは失敗し（`invalid arguments for openFile: filePath is required`）、アダプターには聞きません。モデルが送るものが、渡したスキーマに合っているとは、信用しません。
- 使えないツール（知らないもの、アダプターが宣言していないもの）の呼び出しは、プロトコルのエラー（コード `-32602`）で、アダプターには何も送りません。
- `getWorkspaceFolders` は、サーバーが登録の内容から答えるので、`workspaceFoldersChanged` に追従します。

MCP のプロトコル自体（握手、版の交渉、`tools/list`、`tools/call`、エラー）は、MCP の公式の Rust SDK である `rmcp` クレートが処理します。`mcp` モジュールの中で、このクレート自身の型の後ろに置いています。サポートする最小の Rust が 1.88 なのは、`rmcp` が要求するからです。MCP が定めていないメッセージ（`ide_connected`、`selection_changed` など）は、SDK の独自の通知として扱います。

### Claude に送る通知

| 通知                    | いつ                                                           |
|-----------------------|--------------------------------------------------------------|
| `selection_changed`   | アダプターが、新しい選択範囲を知らせたとき                                        |
| `at_mentioned`        | 利用者が、選択範囲かファイルを、参照として送ったとき（`filePath`、`lineStart`、`lineEnd`） |
| `diagnostics_changed` | アダプターが、診断の変更を知らせたとき（`{ "uris": [...] }`）                     |

VS Code の拡張機能は、診断が変わるのを見るたびに（変化のイベントごとに1つ、ファイルの URI をつけて）`diagnostics_changed` を送ります。Claude Code 2.1.322 は、これを受け付けません（コードに出てきません）。自分で編集する前後に、`getDiagnostics` で診断を取りに来ます。ほかのクライアントは受け付けるかもしれないので、送ります。

### Claude Code が自分から送るもの

Claude Code 2.1.322 のコードから分かること（プログラムを読んだものであって、仕様ではありません）。該当すると書いてあるものは、ターミナルで Neovim アダプタに対して確かめました。どれも、エディタが何かをしたことへの答えではありません。

- 通知 `ide_connected`。ハンドシェイクの直後に、Claude Code のプロセスつきで来ます。
- エディタへのツール呼び出し: `closeAllDiffTabs`（接続の直後と、差分を閉じるとき）、`openDiff` と `close_tab`（差分）、`getDiagnostics`（編集しようとするファイルについて、編集の前後と、全ファイルについて。戻ってきた `uri` が、編集したファイルと（両方を正規化したうえで）違うと、`Diagnostics file path mismatch` として結果を捨てます）、`set_permission_mode`（`{ mode: "ask" | "skip_all_permission_checks" }`。許可モードが変わるたびに）。
- **Claude Code が求める `uri` は、そのまま返してほしい `uri` です。** 2つを正規化し（`file://` などを取り除きます）、シンボリックリンクは解決しないので、リンク経由で名指したファイルは、実パスで返ってきてもそのファイルとは見なされません。アダプタは、ファイルを実パスで探し、求められた `uri` のままで答えます（Neovim のアダプタで、リンクの下のワークスペースで確認しました。リンク経由で求めた `uri` が、そのファイルの診断とともに返ってきました）。確認していないのは、Claude Code が編集の前後に自分で行う呼び出しで、`Diagnostics file path mismatch` が出るのはそこです。
- エディタからの通知で受け付けるのは、`selection_changed`、`at_mentioned`、`log_event`、MCP のログメッセージです。`getOpenEditors`、`getCurrentSelection`、`getLatestSelection`、`checkDocumentDirty`、`saveDocument`、`getWorkspaceFolders` は使いません。
- **ハンドシェイクの直後に届いた通知は、捨てられます。** Claude Code は、接続してからしばらくあとに、通知を受け取るものを用意し、その時間は回によって違います（確認: すぐに送った `selection_changed` は一度も届かず、25 ms や 50 ms 後に送ると3回ずつ3回とも届き、100 ms と 150 ms 後は3回中2回届きました）。サーバーは、通知が受け取られたかどうかを知ることができません。通知には返事がなく、MCP の仕様（2025-11-25 の「Lifecycle」）にも、クライアントがいつ通知を受け取れるかの合図がないからです（最初の `tools/list` も、合図ではありませんでした）。そのため、記憶している状態（選択範囲）を、すぐに送る再送に加えて、ハンドシェイクの 250 ms・500 ms・1 秒・3 秒後にも送り直します（`claude_state_resends`）。500 ms は、VS Code の拡張機能が接続のあとに選択範囲を1回送る時刻です（コードから読みました）。250 ms・1 秒・3 秒（測定した時刻）では、空いているマシンで10回中10回がモデルに届きました。CPU も忙しい状態（16 コアに `stress-ng` を 32 ワーカー、load average は 28〜42）で、Neovim で選択範囲を作ってから Claude Code を起動し、時刻に 500 ms を含めた測定では、12回中12回が届きました。そこでは Claude Code の起動が遅く、アダプタが登録してから 10〜21 秒後に接続しました（空いているマシンでは 2.4 秒）。サーバーのログには、どの再送で届いたかが出ないので、これらの測定からは、どの時刻も外せるとは言えません。時刻は変えていません。あとの通知は受け付けられるので、これは接続後の数秒だけの話です。

### VS Code の拡張機能がすること

VS Code の拡張機能は、このサーバーが代わりを務める IDE 側そのものなので、そのコード（2.1.322。読んだものであって、仕様ではありません）が、エディタが何を答えるかの基準になります。このプロトコルのクライアントが当てにしてよいことは次のとおりです。

- 一度に1つのクライアントだけを相手にします。新しい接続は、その前の接続を閉じます。このサーバーは複数を保ちます（「1つのワークスペースに複数の CLI」を参照）。
- **接続したあと 500 ms 待って、最後に報告された選択範囲（`selection_changed`）と、ためておいたテレメトリのイベント（`log_event`。このサーバーには使い道がありません）を送ります。** 待つのは、接続したばかりのクライアントが、通知を受け取る準備がまだできていないためです（「Claude Code が自分から送るもの」を参照）。
- 診断が変わるたびに、ファイルの URI をつけて `diagnostics_changed` を送ります。
- `filePath` を受け取るツールは、相対パスも受け取り、最初のワークスペースフォルダからのパスとして扱います。結果は、インデント2つの JSON で書いたテキストで、メッセージは、上と下の表にあるものです。
- `openFile` は、ドキュメントの先頭から単純な検索で `startText` を探し、その後ろから `endText` を探します。ドキュメントは、最後の改行のあとにもう1行あるものとして数えます。
- Claude Code の編集の前後の診断の追跡（エディタが診断を出すのを待ちます）は、このプロトコルではなく、拡張機能の内部で行われます。編集されたファイルについて、最初の更新を最大 750 ms 待ち、そのあとは 150 ms 更新がなくなるまで待ち、全体で 1500 ms まで（どのエディタにも表示されていないファイルは 1000 ms まで）です。こうした待ちのないアダプタは、編集の前に持っていたものを答えます。Neovim のアダプタは、同じ時間だけ待ちます（[NVIM](NVIM.md) の「診断」を参照）。

### 遅い読み手

送られたものを読まないクライアントが、ほかのクライアントや、ワークスペースを止めてはいけません。Claude Code への通知は、クライアントごとの待ち行列に入れ、そのクライアントの専用のタスクが送ります。送るときに、待つことはありません。

- **状態** の通知（選択範囲）は、まだ待っている、同じメソッドの通知を置き換えます。だから、遅いクライアントには、状態の履歴ではなく、いまの状態が届き、最新のものが失われることはありません。
- それ以外（メンションされたファイル）は、順番を保ちます。1 つのクライアントに 64 件より多くが待っているときは、いちばん古いものを捨てます。
- ワークスペースの持ち主が読むイベント（`Workspace::next_event`）は、情報で、同じように渡します。256 件より多くが待つと、新しいものを捨てて、数えます（`dropped_events`）。選択範囲を Claude Code に渡すことは、だれかがそれを読むことに、依存しません。

### 1 つのワークスペースに、複数の CLI

WebSocket の接続は、1 本ごとに別のクライアントです。サーバーは、1 つのワークスペースで、複数を受け付けます（VS Code の拡張は、最新の 1 本だけを残します）。差分は、それを開いた接続のものです。その接続が閉じたとき、または、いなくなったときに、閉じます。

## アダプター側

### 通信の経路

- `$XDG_RUNTIME_DIR/claude-ide-server/adapter.sock` の Unix ドメインソケットです。置き場所のディレクトリはモード 0700、ソケットのファイルはモード 0600 です。
- JSON-RPC 2.0 を、LSP と同じ `Content-Length` のフレーミングで使います。すでに LSP クライアントを持つエディタは、そのトランスポートを再利用できます。Neovim 0.12 で確認しました。`vim.lsp.rpc.connect(path)` は Unix ソケットに接続でき、アダプタはリクエストと通知を送れ、サーバーからのリクエストにも答えられ（`server_request` ディスパッチャ）、サーバーが接続を閉じると `on_exit` が呼ばれて `is_closing()` が true になります。接続に失敗した場合もエラーは起きません。Neovim は警告を表示するだけで、`on_exit` は続きません。そのためアダプタは、まず自前の接続を試して閉じ（サーバーは何も言わずに閉じる接続を無視します）、それがうまくいったときだけ `vim.lsp.rpc` で接続します。これにより、メッセージを出さずに再試行することもできます。[Neovim アダプタ](NVIM.md)を参照してください。
- どちらの側からも、要求と通知を送ります。接続がそのままワークスペースです。接続が閉じたら、サーバーは、そのワークスペースの WebSocket のクライアントとポートを閉じて、ロックファイルを消します。

### メッセージ

アダプター → サーバー:

| メッセージ                     | 種類   | 引数                                                                                   |
|---------------------------|------|--------------------------------------------------------------------------------------|
| `register`                | 要求   | `ideName`、`pid`、`workspaceFolders`、`methods`（実装しているサーバー→アダプターのメソッド）→ `{ "port": n }` |
| `workspaceFoldersChanged` | 通知   | `workspaceFolders`（ロックファイルを書き直します）                                                   |
| `selectionChanged`        | 通知   | `filePath`、`text`、`selection`                                                        |
| `diagnosticsChanged`      | 通知   | `uris`                                                                               |
| `atMention`               | 通知   | `filePath`、`lineStart`、`lineEnd`                                                     |

サーバー → アダプター:

| メッセージ                 | 種類   | 引数 → 結果                                                                                                                                                 |
|-----------------------|------|---------------------------------------------------------------------------------------------------------------------------------------------------------|
| `openFile`            | 要求   | `filePath`、`preview`、`startText`、`endText`、`selectToEndOfLine`、`makeFrontmost` → `{ filePath, languageId, lineCount, isDirty, isUntitled, selection? }` |
| `getOpenEditors`      | 要求   | → `{ tabs: [{ uri, isActive, label, languageId, isDirty, ... }] }`                                                                                      |
| `getCurrentSelection` | 要求   | → 選択範囲、または `{ success: false }`                                                                                                                         |
| `getLatestSelection`  | 要求   | → 選択範囲、または `{ success: false }`                                                                                                                         |
| `getDiagnostics`      | 要求   | `uri?` → `[{ uri, diagnostics: [{ message, severity, range, source }] }]`                                                                               |
| `checkDocumentDirty`  | 要求   | `filePath` → `{ isDirty, isUntitled }`。ドキュメントが開いていなければ `{ success: false }`                                                                             |
| `saveDocument`        | 要求   | `filePath` → `{ saved }`。ドキュメントが開いていなければ `{ success: false }`                                                                                           |
| `openDiff`            | 要求   | `oldFilePath`、`newFilePath`、`newFileContents`、`tabName`、`diffId` → `{ accepted: true, contents }` か `{ accepted: false }`。ユーザーが決めたときに答える                |
| `closeDiff`           | 要求   | `tabName`。そのタブのうち、その差分だけを閉じたいときは `diffId` も → 何でもよい                                                                                                     |
| `closeAllDiffs`       | 要求   | → `{ closed: n }`                                                                                                                                       |
| `shutdown`            | 通知   | サーバーが止まるとき                                                                                                                                              |

位置は `{ line, character }` です。`line` は 0 始まり、`character` は UTF-16 のコード単位（LSP の決まり）で、範囲の終わりは含みません。エディタ自身の単位からの変換は、アダプターが行います。**（仮定）** CLI は、選択範囲から行数を数えるだけなので、`character` を間違えても、Claude に見えるものは変わりません。

### アダプターが報告する、エディタの状態

アダプターが送るものは、サーバーが検査します。足りない項目や、型の違いを、推測で補いません。要求への答えなら、ツール呼び出しを失敗にして、誤りの場所をテキストに入れます（たとえば `the editor's answer to getOpenEditors is not valid: $.tabs[1].isDirty: expected a boolean`）。通知なら、その通知は転送せず、ワークスペースの持ち主に知らせます（`MalformedNotification`）。

- **選択範囲** は `{ filePath, text, selection: { start, end } }` です。`start` と `end` は位置です。これが `selectionChanged` の引数で、選択範囲があるときの `getCurrentSelection` と `getLatestSelection` の答えです。ないときの答えは `{ "success": false, "message": ... }` です（`message` は省略できます）。選択のないカーソルは、`text` が空で、`start` と `end` が等しい選択範囲です。`isEmpty` は、サーバーが範囲から求めます。
- **`atMention`** は `{ filePath, lineStart, lineEnd }` で、0 始まり、`lineEnd` は最後の行です。
- **`filePath`** は、絶対パスです（Unix では `/` で始まります。Windows では、ドライブと区切り文字（`C:\Users\u\a.lua`）か、区切り文字で始まります。Claude Code は Node なので、そのように扱います: `path.win32.isAbsolute`）。Claude Code は、これから、見せるものを決めます。相対パスだと、Claude Code が動いているディレクトリが基準になりますが、それはエディタのものではありません。
- **Windows のパス**は、ネイティブのパスを、省略せずに書いたものです。エディタは、ファイルを 8.3 の短い名前（`C:\Users\RUNNER~1\a.lua`）で知っていることがありますが、Claude Code は、自分の作業ディレクトリ（長い名前を持っています）と、パスをテキストとして比べます。そこで、Neovim アダプタは長い名前（実在するパスで、元の大文字小文字のまま）を報告します。それ以外では、サーバーはエディタの報告を変えません（区切り文字やドライブレターの大文字小文字は、そのままです）。サーバーが `filePath` から作る `fileUrl` は `file:///C:/Users/u/a%20b.lua` で、共有のパスでは `file://server/share/a.lua` です。アダプタが作る `uri` はそのアダプタのものです（Neovim の `vim.uri_from_fname` も同じ形を書きます）。ツール呼び出しの相対的な `filePath` は、ワークスペースの最初のフォルダと、そのフォルダが使う区切り文字で結合され、`..` はドライブや共有より上には出ません（`crates/core/src/paths.rs`。文字列だけを扱い、パスの2つの書き方の両方を、どのシステムでもテストしています）。
- **`getOpenEditors` への答え**は `{ tabs: [ ... ] }` です。タブには、このプロトコルのどのクライアントも受け取る5つがあり、5つとも必須です（`uri`、`isActive`、`label`、`languageId`、`isDirty`）。VS Code の拡張機能は、タブにさらに加えており、アダプタはどれを省いてもかまいません。`isPinned`、`isPreview`、`groupIndex`、`viewColumn`（そのタブがいるグループと、その列）、`isGroupActive`、`fileName`、`lineCount`、`isUntitled`、そしてアクティブなタブには `selection: { start, end, isReversed }` です。あるものはそのまま渡し、あれば検査します。
- **`openFile` への答え**は `{ filePath, languageId, lineCount, isDirty, isUntitled }` で、`startText` が渡されたときは、さらに `selection` を持ちます。これは、テキストを探した結果で、`"text"`（`startText` のテキストを選択した）、`"range"`（`startText` から `endText` まで）、`"positioned"`（`startText` は見つかってカーソルがあるが、`endText` は見つからなかった）、`"not_found"` のどれかです。サーバーは、結果を VS Code の拡張機能と同じように書きます。`startText` が渡されたときはメッセージだけ（`Opened file and selected text "..."` など）、ファイルを最前面にするとき（`makeFrontmost`。false と書かれていなければ true）は `Opened file: <path>`、それ以外は詳細を JSON で返します。開けないファイルは、アダプタのエラー（`File not found: <path>`）で、ツール呼び出しは失敗します。絶対パスでないパスは、アダプタに聞く前に、最初のワークスペースフォルダからの絶対パスに直されるので、アダプタは絶対パスを受け取ります（VS Code の拡張機能と同じです）。
- **`checkDocumentDirty` と `saveDocument` への答え**は、それぞれ `{ isDirty, isUntitled }` と `{ saved }` で、開いていないドキュメントには `{ "success": false }` です（サーバーは `Document not open: <path>` と言います）。`saved` は、書くものがなかった、または書けなかったときに false です。
- **`diagnosticsChanged`** は `{ uris: [ ... ] }` で、診断が変わったファイルの URI です。これは出来事（イベント）で、それぞれがファイルを名指しし、どれもほかを置き換えず、あとから接続した Claude Code には伝えません。
- **`getDiagnostics` の答え**（引数は `{ uri }`、すべてのファイルなら引数なし）は `[ { uri, diagnostics: [ { message, severity, range: { start, end }, source? } ] } ]` です。`severity` は、`"Error"`、`"Warning"`、`"Information"`、`"Hint"` のどれかです。空の一覧も、答えです。求められた `uri` については、項目の `uri` は、求められたものを書かれたままで返し（「Claude Code が自分から送るもの」を参照）、答えはいまのファイルの診断です。エディタの下で変更されたばかりのファイルの診断は、アダプタが短い時間だけ待つのが望ましいです。

サーバーは、これらを Claude Code が期待する形で渡します（上の通知を参照）。`selectionChanged` は `selection_changed` になり（`fileUrl` と `isEmpty` が加わります）、`atMention` は `at_mentioned` に、`diagnosticsChanged` は `diagnostics_changed` になり、答えは、VS Code の拡張機能が書く形のツールの結果のテキストになります（たとえば、`getCurrentSelection` には `success` があり、`getLatestSelection` にはありません）。あとから接続した Claude Code には、そのとき現在の `selection_changed`（最後のもの）が送られ、ユーザーがいま見ている選択範囲から始められます。最初のものが捨てられることがあるので、ハンドシェイクのあとに数回、送り直されます（「Claude Code が自分から送るもの」を参照）。

**差分。** ファイルを書くのは、エディタではなく Claude Code です。エディタは、書く内容を答えとして返します（VS Code の拡張機能は、ユーザーが承認したとき、`FILE_SAVED` と、そのときのファイルの内容を答えます。内容は、差分の中で編集されたものかもしれません。Claude Code は、2つ目のテキストを読んで使い、`FILE_SAVED` 以外は、承認されなかったものとして扱います）。そのため、次のようになります。

- `openDiff` は、ユーザーが決めたときに答えます。それまでは答えません。サーバーは、これに時間制限を設けません（アダプタへのほかのリクエストには制限があります）し、ほかのものがこれを待つこともありません。答えは `{ accepted: true, contents }`（`contents` がなければ、受け付けません。Claude Code がファイルを書けないからです）か `{ accepted: false }` です。サーバーは、これらを、`FILE_SAVED` と内容、`DIFF_REJECTED` と タブ名に変えます。
- サーバーは、差分ごとに番号 `diffId` を振ります。表示中の差分と同じ名前の新しい `openDiff` は、その差分を置き換えます。アダプタは、古いほうを、却下として終わらせます。差分を頼んだ Claude Code が、呼び出しを取り消したり、いなくなったりしたら、サーバーは、`tabName` とその `diffId` をつけて `closeDiff` を送ります。誰にも聞けない差分が、画面に残らないようにするためです。アダプタは、その名前で表示されているのがその差分のときだけ閉じます（新しいものには触りません）。Claude Code からの `close_tab` には `diffId` がなく、その名前の差分なら、どれでも閉じます。
- `closeAllDiffs` には、いくつ閉じたかを答えます（`{ closed: n }`）。

### バージョン

`register` は、整数の `protocolVersion` を持ちます。ここに書いてある版は `1` です。サーバーは、知らない版のアダプターを断ります。メソッドは、版を上げずに足せます。アダプターは、実装しているものを `methods` に並べます。

### `register` の詳細

- `register` は、最初のメッセージで、要求でなければなりません。ほかのものが最初に来たときは、要求ならエラーで答え、通知なら、接続を閉じるだけです。`register` を 2 回送るのも、エラーです。
- 引数は、`protocolVersion`（整数）、`ideName`（空でない文字列）、`pid`（正の整数）、`workspaceFolders`（空でない文字列の配列）、`methods`（文字列の配列）です。足りない引数や、型が違う引数は、エラーです。
- 結果は `{ "port": <整数> }` です。この時点で、そのポートは待ち受けていて、ロックファイルもあります。
- アダプターは、10 秒以内に送らなければなりません。送らない接続は、閉じられます。
- `workspaceFoldersChanged` の引数は、`{ "workspaceFolders": [...] }`（空でない）です。それ以外は、無視されます。
- アダプターが `methods` で宣言していないメソッドは、呼ばれません。登録したアダプターが、サーバーの知らない要求を送ると、`-32601` が返ります。

エラーコードは、JSON-RPC のもの（引数が悪いときは `-32602`、知らないメソッドは `-32601`）と、このプロトコルの 3 つです。`-32000` はプロトコルの版に未対応、`-32001` はワークスペースを用意できなかった（ポートかロックファイル）、`-32002` は最初のメッセージが `register` ではなかった、または `register` が 2 回来た、です。`register` へのエラーのあと、サーバーは、接続を閉じます。

サーバーがワークスペースを手放すときは、通知 `shutdown` を送って、接続を閉じます。接続が終わったときに、答えを待っている要求は、失敗します。

## core クレートの構成

このクレートは、tokio の上で動きます。`async` の関数は、tokio のランタイムの中で呼びます。層のあいだの共通の受け渡しには、tokio の I/O のトレイト（`AsyncRead`、`AsyncWrite`）を使います。それ以外の tokio の型（チャネル、タスク）と、下の層のライブラリの型は、このクレートの公開されたインターフェースに出しません。

外のライブラリは、それぞれ、このクレート自身の型の後ろに置きます。内側は、その型だけを知っています。層は 3 つです。

- **Claude 側:** WebSocket サーバー（`ws`）、MCP の処理、ロックファイル（`lock`）。
- **中間:** ワークスペース（`workspace`）、ツール呼び出しの振り分け、ツール・選択範囲・診断についての、このクレート自身の型。
- **アダプター側:** アダプターとの通信路、`register` のやりとり、要求（`adapter`）と、JSON-RPC の区切り（`jsonrpc`）。

各側は、互いを知りません。`adapter` には、ポートもロックファイルも出てきません。アダプターが登録すると、登録の内容を上へ渡し（`Registering`）、答え（ポートか、拒否）を待ちます。両者が出会うのは `workspace` モジュールです。登録ごとに、WebSocket サーバーを起動し、ロックファイルを書き、アダプターにポートを渡し、それぞれの寿命を結びつけます。`ws` と `lock` は、アダプターのことを何も知りません。

この設計がすでに「変わるかもしれない」と言っている所に、3 つの境界を、わざと引いています。

1. **アダプターとの通信路。** Unix ソケット、Windows では名前付きパイプ。これより上は、Unix ソケットの型ではなく、待ち受けが受け付ける、双方向のバイトストリームを使います。
2. **MCP の SDK。** `rmcp` を使うなら、その型は、Claude 側の中にとどめます。中間とアダプター側は、このクレート自身の型を使います。SDK の新しい版や、別の SDK に替えても、1 つの層だけで済みます。
3. **ファイルシステムと環境。** ロックファイルのディレクトリ、実行時のディレクトリ、`pid` が生きているかの確認は、設定として外から渡します。テストでは、一時ディレクトリを渡します。

それ以外は、前もってトレイトの後ろには置きません（TCP そのもの、ロックファイルの JSON の形）。境界は、変わることが分かったときに足します。その前には足しません。

1 つだけ、境界から、わざと外してあります。トークンの出どころです。トークンは、このマシンのほかのプロセスを、ワークスペースから遠ざける、唯一の鍵です。だから、いつも OS の乱数から作り、それが失敗したときは、弱いトークンを使わずに、ワークスペースを断ります。呼び出し側が変えられる設定には、入れません。テストは、（失敗する場合を試すためや、トークンをあらかじめ知るために）クレートの `test-support` という feature を通して、差し替えられます。この feature は、このクレート自身のテストでだけ有効で、ふつうのビルドでは、有効になりません。

## 起動から終了までの流れ

1. サーバーが起動して、アダプターのソケットで待ち受けます。
2. アダプターが接続して、`register` を送ります。
3. サーバーは、`127.0.0.1` の空いているポートを選び、OS の暗号論的乱数から 128 ビットのトークンを作り、ロックファイルを原子的に書き（一時的な名前で書いてから、名前を変える）、ポートを返します。
4. CLI が、ロックファイルを見つけて、つないで、認証します。選択範囲と診断は、CLI へ流れます。CLI のツール呼び出しは、アダプターへの要求になります。
5. アダプターが切れる（か、落ちる）と、サーバーは、そのワークスペースの接続を閉じ、ロックファイルを消し、保留中の要求を失敗にします。
6. 終了するとき、サーバーは、アダプターに `shutdown` を送り、自分が書いたロックファイルをすべて消します。

サーバー自身が強制終了されると、ロックファイルが残ります。サーバーは、自分が書いたロックファイルを、実行時のディレクトリに記録しておき、次の起動で、まだ残っているものを消します。

## サーバーの実行

`claude-ide-server`（`crates/server` クレート）は、すべてのエディタに共通の1つの実行ファイルです。`claude-ide-server --help` でスイッチの一覧が出ます。`--socket`（アダプタの接続先）、`--idle-timeout`（最後のアダプタがいなくなってから、その秒数が経ったら終了する）、`-v` / `-q`（ログの詳しさ）。ログは `tracing` を通して標準エラーに出ます。`CLAUDE_IDE_SERVER_LOG` か `RUST_LOG` があれば、スイッチの指定より優先されます。`SIGINT` か `SIGTERM`（Windows では Ctrl-C か Ctrl-Break、コンソールを閉じること、システムのシャットダウン）が来るまで動き続け、来たらすべてのアダプタに `shutdown` を伝えて、ロックファイルとポート（と、自分で作ったソケット）を片付けます。終了コードは、0 が指示どおりの停止、1 が起動できなかった（またはソケットが閉じた）、2 がコマンドラインの誤り、3 が時間内にワークスペースを閉じられなかった、です。

### アダプタ用のソケットの出どころ

サーバーは、どう起動されたかを気にしません。手で起動された場合、監督プロセスがソケットを待ち受けて最初の接続で起動した場合（ソケットアクティベーション）、サーバーが見つからなかったアダプタが起動した場合のどれでも同じです。違うのは、待ち受け中のソケットをどう手に入れるかだけで、それは小さなトレイト `SocketSource`（`crates/server/src/activation.rs`）の裏に隠してあります。当てはまる最初の取得元が使われます。

| 取得元            | 対象                                   | 方法                                                                       |
|----------------|--------------------------------------|--------------------------------------------------------------------------|
| 受け取る           | systemd、および同じ規約に従う他の監督プロセスやコンテナランタイム | ソケットが、引き継いだファイルディスクリプタですでに待ち受けている（`LISTEN_PID`、`LISTEN_FDS`）             |
| launchd から受け取る | macOS の launchd                      | ソケットは、ジョブのプロパティリストにある名前（`adapter`）で求めます（`launch_activate_socket`）。       |
| 自分で作る          | それ以外のすべて。既定                          | サーバーが自分でソケットを作る。0700 のディレクトリの中に、モード 0600 で（Windows では、ユーザーだけが開ける名前付きパイプ） |

受け取ったソケットは、サーバーが消してよいものではありません。サーバーが終了してもそのまま残り、次の接続で監督プロセスがサーバーをもう一度起動します。`--idle-timeout` があれば、オンデマンドで起動したサーバーが居座り続けることはありません。`contrib/` に各システム向けのファイルがあり、どれも本物で試しました。`contrib/systemd` は本物の systemd で（アダプタが接続するまでサービスは起動せず、アイドル時間が過ぎると終了し、ソケットは残ります）、`contrib/launchd` は CI の macOS ランナーで試しました。そこでは `crates/server/tests/launchd.rs` が、同梱のプロパティリストをユーザーのドメイン（`gui/<uid>`。ランナーにはあります）に読み込み、同じ4つのことを確かめます。読み込んだあとは何も動いていないこと、最初の接続でサーバーが起動し、launchd が渡したソケットを提供すること、アイドル時間が過ぎるとソケットを残したまま終了すること、次の接続でまた起動することです。

**アダプタがそれを探す場所。** 既定では、アダプタは、それぞれ、サーバーと同じ場所を割り出します。場所は、サーバーと、それを読むアダプタのために、`CLAUDE_IDE_SERVER_SOCKET` で1回だけ決めることもできます（サーバーでは `--socket` が、Neovim アダプタでは `socket` オプションが、これより優先されます）。監督プロセスや、既定の場所を共有してはいけないテストが、これを設定します。`claude-ide-server --print-socket` は、その場所（`--socket` や環境変数が言うもの、なければ既定）を出力して終了します。既定の場所を割り出せないアダプタのためのもので、Windows の Neovim がそうです。Windows ではパイプの名前にユーザーのセキュリティ識別子が入っていて、Neovim はそれを与えてくれません。そのアダプタは、`server.command` が指す実行ファイルに、1回だけ尋ねます。

システムごとの違いは、そのシステム専用の取得元に吸収し、システムで決まる箇所では `cfg` で選びます。

- **systemd**（Linux）: 受け取る取得元です。
- **launchd**（macOS）: launchd のソケットアクティベーションは、環境変数ではなく `launch_activate_socket` を通して、名前でソケットを渡します。この取得元は `adapter` という名前のソケットを求めます。launchd がプロセスを起動したのでない場合（サーバーを手で動かしたとき）や、そのようなソケットのないプロパティリストから起動された場合には当てはまらず、そのときはサーバーが自分でソケットを作ります。この呼び出しは C なので `unsafe` が要り、ワークスペースはそれを禁止しています。そこで専用のクレート `claude-ide-launchd` に置きました。`unsafe` があるのはここだけで（使う箇所ごとに理由を書いてあります）、所有権つきのファイルディスクリプタ（`OwnedFd`）を返すので、ほかの部分は `unsafe` なしのままです。プロパティリストの `SockPathName` には `$TMPDIR` や `~` が使えないので、`contrib/launchd` のファイルでは、その場所に `@SOCKET@` があり、ファイルの中の手順で、アダプタが既定で探すパスに置き換えます（ディレクトリも作ります。launchd は作りません）。ユーザーエージェントを読み込める launchd のドメインがないマシン（誰もログインしていないセッション、コンテナ）では、この試験は動かせません。そう表示して終了しますが、`CLAUDE_IDE_REQUIRE_LAUNCHD=1` が設定されていれば（CI がそうしています）失敗にします。
- **タスクスケジューラ**（Windows）: タスクは接続では起動できないので、ソケットアクティベーションはありません。サーバーはログオンしたときから動き（`contrib/windows`）、アダプタは名前付きパイプ `\\.\pipe\claude-ide-server-<sid>` に接続します（`--socket` で別の名前も指定できます）。パイプは、コアクレートの `PipeListener` が Unix ソケットの代わりに作り、サーバーのほかの部分は違いを知りません。このパイプに特有のことは次のとおりです。
  - 名前にはユーザーのセキュリティ識別子（SID）が入っています。パイプの名前はマシン上のすべての人に共通だからです。パイプのアクセスリストにはそのユーザーだけがいて、ほかのマシンからのクライアントは拒否されます。名前の最初のインスタンスは「最初のもの」として作られ、名前がすでに使われていればシステムが拒否するので、同じ名前での2つ目のサーバーは、Unix と同じように、起動に失敗します（終了コード 1）。パイプは最後のハンドルとともになくなるので、死んだサーバーが置き換えの要るものを残すことはありません。
  - `unsafe` が要る呼び出し（プロセスが生きているかどうか、ユーザーが誰か、アクセスリストつきのパイプを作ること）は、launchd のものと同じように、専用のクレート `claude-ide-windows` に置いてあります。
  - ロックファイルは `CLAUDE_CONFIG_DIR` に、なければ `%USERPROFILE%\.claude\ide` に置きます（Windows で Claude Code、つまり Node がホームディレクトリを取るのが `USERPROFILE` だからです）。モードはありません。ファイルは、ユーザーのディレクトリが与えるものを持ちます。
  - **タスクスケジューラは、タスクをプロセスの強制終了で止めます。** ランナーで、止めたタスクの最後の結果は `267014`（ユーザーによる終了）で、サーバーは後始末をする機会を得ませんでした。そこで、ロックファイルとその記録は、それぞれ「閉じたら削除」という印のハンドルで持たれ、プロセスがどう終わっても、なくなったときにシステムがそれを閉じます。（読む側、たとえば Claude Code は、これに妨げられず、ファイルを置き換えることもできます。書き直しはその方法です。停電で残ったものや、これを行わないシステムで残ったものは、Unix と同じように、次のサーバーが消します。）
  - 手で動かしたサーバーのコンソールのイベント: Ctrl-C と Ctrl-Break は「interrupted」、コンソールを閉じることとシステムのシャットダウンは「terminated」で、どちらも `SIGINT` や `SIGTERM` と同じようにサーバーを終了させます。
  - `contrib/windows/claude-ide-server.xml` がそのタスクです。宣言は、タスクスケジューラが書き出すのと同じ UTF-16 になっています。`schtasks` プログラムがそれしか読めないからです。ファイルの中の手順は PowerShell を使い、そちらにはテキストが渡されます（`Register-ScheduledTask -Xml`）。タスクには環境変数がないので、サーバーはユーザーのパスを使います。
  - CI の Windows ランナーで試したこと: コアのすべてのテスト、実行ファイルのテスト（アダプタがパイプで登録し、Claude Code の代役がロックファイルのトークンで接続してツールを呼ぶ。強制終了したサーバーがロックファイルを残さない。2つ目のサーバーは拒否される。アイドルでの終了）、そして `crates/server/tests/task_scheduler.rs`。後者は、同梱のファイルを登録し、タスクを開始し、アダプタと代役で同じことをして、タスクを止め、パイプがなくなっていて、ロックファイルが残っていないことを確かめます。この試験は `CLAUDE_IDE_TRY_TASK_SCHEDULER=1` があるときだけ動きます（タスクはユーザーのパスを使うので、自分のサーバーがあるマシンから、試験がそれを取ってはいけません）。CI がそれを設定します。
  - Windows で Claude Code がロックファイルをどう扱うか。コード（2.1.322）から読んだことで、Windows の Claude Code では試していません。`<設定ディレクトリ>/ide` の `*.lock` を一覧し、`pid` のプロセスが生きているかを尋ね（`process.kill(pid, 0)`）、自分の作業ディレクトリ（ドライブレターは大文字、NFC）を、`workspaceFolders` のそれぞれと、包含で比べます。接続先は `127.0.0.1` で、別のアドレスは、エディタが Windows にある WSL のためのものです（`runningInWindows`）。
  - Neovim アダプタを Windows のランナーで動かしました（Neovim 0.12.6。`crates/server/tests/nvim.rs` のテストで、いまはどのシステムでも動きます）。パイプで登録し、`:cd` に追従し、選択範囲、開いているエディタ、診断を報告し、ファイルを開き、確かめ、保存し、Claude Code が提案する変更を見せてユーザーの判断を受け取り、サーバーを切り離して起動し、再起動したあとにまた見つけます。[NVIM](NVIM.md) の「Windows」を参照してください。
  - まだしていないこと: アダプタからタスクをオンデマンドで起動すること（アダプタは実行ファイルを自分で、切り離して起動します。タスクは起動しません）。そして WSL で、これは Issue #24 です。

待ち受けている相手がいないことに気づいたアダプタは、この同じ実行ファイルを自分で起動します（Neovim アダプタは、止められない限りそうします）。接続することがサーバーを起動するきっかけで、それに答えるのが監督プロセスかアダプタかは問いません。そのときサーバーはエディタの子プロセスではなく、`--idle-timeout` があれば、最後のアダプタがいなくなったところで終了します。2つのアダプタが同時にそうしても安全です。同じソケットで2つ目のサーバーは、起動を拒否する（終了コード 1）からです。

## セキュリティ

- 待ち受けは、すべて `127.0.0.1` です。アダプターのソケットは、モード 0700 のディレクトリの中にあり、ソケット自身も 0600 です（Windows では、パイプのアクセスリストにユーザーだけがいて、ほかのマシンからのクライアントは拒否されます）。
- トークンは、WebSocket へのアップグレードのたびに確かめます。Web ページは、そのヘッダーを付けられないので、ブラウザーは、そのポートと話せません。
- フレームとメッセージの大きさには、上限があります。壊れたメッセージは、その接続だけを閉じます。
- Windows では、パイプの名前は、マシン上のすべての人に共通です。アクセスリストはほかのユーザーをサーバーのパイプに入れませんが、先にその名前のパイプを作ったユーザーは、サーバーを起動できなくし（別のサーバーが待ち受けていると表示されます）、アダプタが送るもの（ワークスペースのフォルダ、選択範囲）を受け取ることができます。これについては、まだ何もしていません。Lua のアダプタは、パイプの持ち主を見ることができません。複数のユーザーが同時に使うマシンで問題になります。
- Claude からのパスは、アダプターが渡したとおりに使います。サーバー自身は、プロジェクトのファイルを読み書きしません。差分が承認されたあとの、ファイルの書き込みは、アダプターの仕事です。

## テスト

- 偽の Claude クライアント（WebSocket）と、偽のアダプター（Unix ソケット）を、同じテストのプロセスで動かします。テストは、握手、認証、すべてのツール、通知、差分、切断、後始末を扱います。テストが共有する部品は、`crates/core/tests/common/` にあります。アダプターの側の接続（`Client`）、一時ディレクトリの上のワークスペースのサーバー（`Fixture`）、Claude Code のクライアント（`MockClaude`）、両方がすでにつながったワークスペース（`Scene`）です。ほとんどのテストは、メモリ上のストリームで動かし、1 つは、本物の Unix ソケットで、全部の経路を動かします（`tests/end_to_end.rs`: 登録し、ロックファイルのトークンで接続し、ツールの一覧を取り、1 つ呼び、切断し、後始末をします）。
- サーバーが送るもの、書くものの、期待する形は、上で書いた、観察した挙動から、`crates/core/tests/fixtures/` のフィクスチャとして書き残します。Claude Code が送る `initialize`、ロックファイルの形、`initialize`・`tools/list`・`tools/call` の結果の形です。形を変えるのは、新しい観察が、そうすべきだと言ったときで、テストを通すためではありません。
- アダプターごとに、自分のテストを持ちます。Neovim のものは、ヘッドレスの Neovim を、本物のサーバーにつないで動かします。

## マイルストーン

1. **M0、サーバーの骨組み。** WebSocket サーバー、ロックファイル、トークン、`initialize`、`tools/list`。偽のアダプター。
2. **M1、読み取りだけのツール。** `getOpenEditors`、`getWorkspaceFolders`、`getCurrentSelection`、`getLatestSelection`、`getDiagnostics`。`selection_changed`、`at_mentioned`。
3. **M2、Neovim アダプタ。** サーバーの実行ファイル（`crates/server`）と、`vim.lsp.rpc` 上の Lua アダプタ。メインのウィンドウだけを登録する。
4. **M3、操作。** `openFile`、`checkDocumentDirty`、`saveDocument`、`diagnostics_changed`。
5. **M4、差分。** `openDiff`、`close_tab`、`closeAllDiffTabs`、そして Neovim アダプタでの承認・却下の流れ。差分を見せる提供元は、差し替えられる。

## 未解決の問い

- WSL。Claude Code とエディタが、Linux と Windows の境界の両側にいる場合（Issue #24）。
- サーバーがいないときに、アダプターがどうするか。再試行するか、どのくらいの間か（Issue #10）。
- CLI は文字列で比べるので、`workspaceFolders` に、パスと、シンボリックリンクを解決した形の両方を書くか。
- プロセスの id は、再利用されることがあります。死んだサーバーが記録した id を、関係のないプロセスが引き継ぐと、そのサーバーが残したロックファイルは、そのプロセスが終わるまで、掃除されません。プロセスの開始時刻も記録すれば、解決します。
